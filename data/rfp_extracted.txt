2. Purpose & Background
2.1 Who Vantage is
Vantage operates a regional trucking and last-mile delivery fleet on behalf of its customers — regional distribution partners. Vantage manages vehicle maintenance, driver assignment, load dispatch, hours-of-service compliance, and fuel/inspection reconciliation across a mixed fleet of company-owned and owner-operator vehicles.
2.2 Purpose of this RFP
Vantage wishes to procure the delivery of a production-ready platform that digitises this end-to-end process. The Platform must manage the complete lifecycle of a dispatch — from load intake and vehicle/driver assignment, through pre-trip inspection and route execution, to post-trip reconciliation, maintenance triggering, and compliance recordkeeping — with a configurable, rule-driven workflow engine.
A reference implementation of this system exists (a Django 5.x application, approximately 51 database tables and 38 view modules). This RFP describes the required capabilities in full so that a Vendor can propose to build the Platform to this specification, whether reproducing the reference stack or proposing an equivalent (see §5.1). The functional requirements herein are the authoritative requirement set.
2.3 The process to be digitised
Load intake → assign vehicle + driver (eligibility & hours-of-service check) → PRE-TRIP: driver inspection (DVIR) → DISPATCH: route execution, stop tracking, exceptions → POST-TRIP: inspection, fuel/mileage capture → MAINTENANCE: fault triage, work order, parts, technician sign-off → COMPLIANCE: hours-of-service log reconciliation, inspection archive → BILLING HANDOFF: mileage/stop data exported to Vantage’s external billing system (export only; no billing logic in this Platform).

4. Scope of Work / Statement of Requirements
This section defines the deliverable requirements the Vendor must propose to build. Each requirement is numbered (FR = functional requirement) so that Bidders may reference them directly in their response and cross-reference against their proposed architecture. Unless a requirement is explicitly marked Optional or Excluded, it is mandatory and must be included in the full-build response.
The Platform is a company-scoped multi-tenant (multi-user) SaaS with six roles and a fully configurable, data-driven workflow. Owner-operator partners must see only their own assigned loads and vehicle data.
4.1 Roles, Permissions & Access Control
FR-1 — Role model. The Vendor shall implement six roles: driver, dispatcher, maintenance_tech, compliance_officer, fleet_admin, and a platform_admin super-user flag layered on top of any role.

FR-2 — Authorisation enforcement. Role checks and company scoping must be enforced at the controller/query (server) layer, not merely hidden in the UI. Cross-company access must be blocked at the data-access layer. Derived capability rules must be supported (e.g. dispatch-write = dispatcher/fleet admin; bulk-revert = fleet admin or platform admin; conditional document-delete).
FR-3 — Company scoping. Owner-operator partner accounts are hard-scoped to their own assigned loads, vehicles, and documents across dashboards, help visibility, and navigation counts.
FR-4 — Impersonation. A Platform Admin may act as any non-admin user (original admin identity retained), with safeguards (no admin-to-admin, no self-impersonation), an in-session warning badge, and an exit control.
4.2 Authentication, Users & Invitations
FR-5 — Authentication. Email/password authentication with password recovery, remember-me, and validation. Password hashing with a strong work factor; a reset window (e.g. 6 hours). Mobile-app session handling for drivers using device-bound refresh tokens.
FR-6 — Invitation onboarding. Admin-initiated user invitations (first/last name, email, role; carrier/company required when role = driver on an owner-operator account); invitee sets password via emailed link; resend-invitation for pending users.
FR-7 — User administration. Searchable/paginated user list with role-filter pills and Active/Invited status badges; edit role, company, and platform-admin flag; per-row impersonate/view/edit.
4.3 Companies, Vehicles, and Driver Records
FR-8 — Carrier companies (Admin CRUD). Manage owner-operator carrier companies: name, primary contact, default document-expiry alert thresholds, and per-carrier vehicle assignment defaults.
FR-9 — Vehicles. Vehicle records: VIN, unit number, make/model/year, fuel type, odometer, registration/insurance expiry, assigned carrier or company-owned flag, current status (active/in-maintenance/out-of-service/retired), and location/base terminal.
FR-10 — Driver records. Driver profile: license class/endorsements, medical-certificate expiry, hours-of-service ruleset assignment (property-carrying vs. passenger, exemptions), home terminal, and eligibility status (active/suspended/ineligible) computed from expiring credentials.
4.4 Vehicle & Equipment Catalogue
FR-11 — Vehicle types. Manage vehicle type/class records: class (tractor, straight truck, trailer, refrigerated trailer), default maintenance-interval templates, and a source marker (manual / telematics_sync / import).
FR-12 — Maintenance interval templates. Per vehicle-type maintenance schedules (mileage-based, time-based, or engine-hour-based) with a configurable “Interval Applies” toggle per vehicle-type/task combination.
FR-13 — Fault/DTC catalogue. Diagnostic trouble code catalogue with a require_technician_note flag; per-vehicle-type applicability exclusions.
FR-14 — Inspection defect categories. Name plus an outcome value (pass / minor-defect / out-of-service); per-vehicle-type exclusions; ordered presentation in the DVIR flow; outcome badges displayed.
FR-15 — Carrier aliases. Map source carrier-name spellings (from imported historical records) to a canonical carrier (case-insensitive, unique source); flag unmapped carriers.
FR-16 — Legacy mappings. Fault and vehicle-type mapping tables to support the legacy importer; seedable and editable in the UI.
4.5 Dispatch & Load Management
FR-17 — Load entity. A central load record with fields, references, and relationships described in Appendix A (§13.1). Human-readable reference format VFO + zero-padded ID (e.g. VFO0000042). Multiple document attachments per load (bill of lading, POD).
FR-18 — Load list view. Company-scoped, status-visibility-gated list with filters by status, route, and originating batch import; per-status configurable columns; optional Group-by-Route (with per-route batch-advance controls); client-side search/sort/pagination; a fixed bulk-action bar (advance / move-back) with selection persisted across pages.
FR-19 — Load detail view. All fields, status badge, Advance card, Move-to-Previous card, document gallery (upload + lightbox + permission-gated delete), and a status-history timeline (from→to, Batch/Reverted pills, actor, captured data, per-stage dwell time).
FR-20 — Edit/lock rule. A load is editable/deletable only while in the default (“Created”) status; once advanced it may only move via advance/revert. Platform-admin-only hard delete for default-status loads.
FR-21 — Documents. Multi-upload of PDF/JPG/PNG via object storage; attachment count on the list.
4.6 Driver Assignment & Eligibility
FR-22 — Assignment form. A rich dispatcher-facing assignment experience: auto-set assignment date and default status; force the dispatching company’s own fleet; Vehicle→Driver cascading selects filtered by current eligibility; a live eligibility-check panel (Eligible / Ineligible — Expired Medical / Ineligible — Hours Exhausted / Ineligible — Vehicle Out-of-Service) computed from vehicle/driver records and the hours-of-service ledger, with rule-specific help text; debounced vehicle search over the assigning company’s own fleet with inline flag-for-maintenance; defect-category list filtered by the vehicle type’s exclusions; and selection persistence across validation-error re-renders.
4.7 Workflow Engine (Statuses & Transitions)
FR-23 — Configurable statuses. Admin configuration of every workflow state without code changes: name, colours, position, default/dispatch flags, role visibility and interactivity arrays, required/optional field sets, batch field sets (Off/Optional/Mandatory for Comment & Stop Count), per-status load columns, route filter/grouping defaults, and compliance/exception flags (compliance-review-queue, out-of-service-eligible, out-of-service-default-on).
FR-24 — Configurable transitions. Allowed next-status edges with optional outcome triggers (pass/minor-defect/out-of-service) and a single default target; dispatch-status and archived destinations excluded from manual advance.
FR-25 — Workflow management UX. Reorder via up/down arrows (auto-resequence); archive/unarchive (soft-retire in-use statuses while preserving history; protect default and dispatch statuses; hard-delete never-used statuses); a “Show Workflow” diagram (top-down flowchart: solid = automatic, dashed = manual, default boxed, arrows coloured and outcome-labelled); and a Role-Visibility matrix modal.
4.8 Eligibility Determination & Outcome Routing
FR-26 — Eligibility determination. Whenever a status collects a driver assignment, the system must determine eligibility: parse the driver’s current hours-of-service ledger against the assigned ruleset; if a medical certificate or license endorsement is missing or expired, treat as ineligible; resolve the applicable ruleset in priority order — driver-specific exemption → carrier default → federal default; compute available drive-time (last reset + elapsed on-duty time); if hours are exhausted or credentials expired, force the outcome to “ineligible” and lock the assignment.
FR-27 — Dual-implementation constraint. This eligibility logic must operate consistently both server-side and in the mobile driver app (assignment confirmation and pre-trip screens). The Vendor must describe how the two implementations will be kept in sync (a single source of truth is preferred — see Risk Register, §11.3).
FR-28 — Outcome routing. For outcome-driven statuses, compute an overall inspection outcome from DVIR defect entries, with priority any out-of-service → out-of-service; else any minor-defect → minor-defect; else pass; route to the transition whose outcome trigger matches; allow a manual override to bypass auto-routing with mandatory reason capture.
4.9 Record & Advance Modal
FR-29 — Shared advance modal. A single shared “Record & Advance” modal reused by the load list, load detail, Maintenance Workbench, and Dispatch Board, populated from the trigger’s data attributes. It must implement: a fast path (immediate advance when a status has no fields, is not outcome-driven, and has exactly one next status); live eligibility/hours-of-service badges and a secondary reset-time input where applicable; the ineligible-driver lock; outcome-driven auto-routing with a calculated-outcome preview; manual override; defect-category filtering by vehicle type; and validation duplicated client and server side.
4.10 Advance / Revert / Bulk Operations & Audit
FR-30 — Advance. Server-side re-validation of all rules (required fields, ineligibility lock, override, dispatch-status guard, role interactivity), persistence, and an immutable audit log entry; a live board re-render when invoked from a workbench.
FR-31 — Revert. Backward-only correction (target position earlier; dispatch status is a valid revert target); logged as reverted.
FR-32 — Bulk advance. Advance each selected load that has exactly one eligible manual transition; enforce batch fields by union rule; logged as batch.
FR-33 — Bulk revert (Fleet Admin+). Move selected loads to a strictly earlier target; logged reverted+batch.
FR-34 — Whole-route advance. Advance an entire route’s eligible loads in one action from the grouped list.
FR-35 — Immutable audit trail. Every status change recorded with actor, timestamps, from/to status, captured inspection data (defect entries, hours-of-service snapshot, eligibility before/after), stop count, batch/reverted flags, and comments.
4.11 Workbenches
FR-36 — Maintenance Workbench. A two-column kanban board (flagged → in-repair) for maintenance technicians/fleet admin/platform admin. Plain advance for flagged→in-repair; the shared modal (“Diagnose & Advance”) for in-repair→outcome. Faceted, cascading filters (vehicle type, fault category, terminal — each reflecting the others), live vehicle/unit-number search, optional group-by-terminal, bookmarkable URLs, and in-place (no-reload) updates.
FR-37 — Dispatch Board. Structurally identical to Maintenance (assigned → in-transit) for dispatcher/fleet admin/platform admin, including the same filters, search, grouping, in-place updates, and a bulk “Move all to In-Transit.”
Note (constraint): In the reference implementation the workbenches resolve their two columns by literal status name, which is a hard dependency despite the otherwise data-driven workflow. The Vendor should preferably resolve columns by status flag rather than name, and must document any name dependency (see §11.3).
4.12 Routes
FR-38 — Routes. Creation (dispatcher/fleet-admin/platform-admin) with planned stops and target departure time; selecting eligible (default-status) loads auto-advances them to the dispatch status; reference RTExxxxx; a stage badge derived from load positions plus compliance status (In-Transit → Post-Trip Complete → Compliance Review Pending → Complete); a “Routes Complete” screen (visible to all, including owner-operator partners) that removes completed routes from the main list.
4.13 Maintenance Triage & Work Orders
FR-39 — Triage workbench (Maintenance Technician+). A per-vehicle, per-fault triage workbench: a vehicle picker with Total/Flagged/In-Repair/Completed counts; faults bucketed Not-Triaged / In-Repair (grouped by vehicle) / Completed; a per-vehicle card with a fault table (fault code, reported date, current & next status), a Compliance-Officer-only Override-Status dropdown (auto-save), an Out-of-Service checkbox, and a per-category severity breakdown with a “Mixed severities” exception; Confirm / Confirm-all actions (blocked while pre-diagnosis faults remain); and out-of-service recomputation on every apply/confirm.
4.14 Hours-of-Service Ledger (Compliance Mechanic)
FR-40 — Hours-of-service allocation. The available drive-time ledger is computed per driver per 24-hour cycle: on-duty time is accumulated from assignment start to end across all loads within a route, cleared at each qualifying reset period, and attributed against the applicable federal or exemption ruleset — guaranteeing cumulative on-duty totals reconcile against the driver’s declared logs. Whether a period counts as on-duty or off-duty is a per-entry override defaulting to the status’s on-duty-default-on flag. This “single reconciled ledger per driver-cycle” invariant must be strongly tested and re-derived server-side.
4.15 Compliance Workbench & Lifecycle
FR-41 — Compliance Workbench (Compliance Officer+). For a fully triaged route, per completed load review the captured DVIR entries, hours-of-service ledger snapshot, and any override flags; declined (out-of-service) vehicles are routed back to maintenance. A summary panel and “Finalize Compliance Review” action create the ComplianceRecord, archive the route’s inspection data, and compute the cycle-hours total.
FR-42 — Compliance record lifecycle. Review Pending → (Compliance Officer “Mark review complete”) → Review Complete, with a paginated history and a per-route snapshot (pass/defect/out-of-service counts, cumulative hours, reviewer, timestamps).
FR-43 — Compliance summaries (generated, not sent). A template-driven internal compliance summary (defect tables, hours-of-service summary) and a fixed external-audit-export summary, both rendered for copy/paste or file export. Automated transmission to a regulatory portal is not in scope (see §11.2); the Vendor may propose it as a follow-on item without pricing it here.
4.16 Bulk Upload
FR-44 — Standard importer (multi-step). File + sheet selection → header/data-row selection → column mapping → per-row validation (carrier/vehicle/fault/dates; fault-vehicle-type exclusions) → historical hours-of-service verification of each row (matched / not found / no ledger data; leading-zero tolerant) → confirmation (creates loads in a transaction; vehicles found-or-created). Stateful upload record (pending → validated → complete) with counts and created-load IDs.
FR-45 — Legacy importer. Sheet picker, auto-detected column layout with manual adjustment, alias-based validation, and “add-alias-and-revalidate” without re-uploading — for one-off migration of historical spreadsheets.
FR-46 — Template & history. Downloadable pre-formatted spreadsheet template (with carrier/vehicle/fault dropdowns); upload history; and a filtered “All loads from Upload #n” view.
4.17 Telematics & Vehicle Data
FR-47 — Telematics web view (read-only, Fleet Admin+). Vehicle index with aggregated mileage/engine-hour counts, a missing-inspection flag, and a source column (telematics_sync / manual / import); a hours-of-service verification panel (Carrier → Driver → all duty-status changes/resets, each linked to its route).
FR-48 — Telematics ingestion. Ingestion via the Partner API (§4.21) and via command-line importers (CSV/JSON, matching vehicles by VIN; a bulk odometer-correction tool by unit number; dry-run/force options). Telematics data is the source of truth for mileage-based maintenance-interval determination.
4.18 Dashboards
FR-49 — Dashboard builder. A user-built Dashboard → Panel → Widget hierarchy with visibility scoping (Me only / By role / Company). At least nine widget types: Active Loads, Total Loads, Loads This Month, Loads by Status, Loads by Carrier, Loads by Vehicle Type, Loads per Month (12), Maintenance Performance by Vehicle Type (staff-only), Unmapped Legacy Carriers (staff-only). At least six chart types (KPI, table, pie, donut, bar, line) on a 12-column grid; optional per-widget compliance-status filter; carrier-safe scoping.
4.19 Reports
FR-50 — Reports placeholder (Optional). A “Reporting coming soon” placeholder area; no functional report engine is required in the core scope. The sidebar should auto-list reports once any exist. A functional Reports module may be proposed separately as a follow-on item.
4.20 Help Guide & Articles
FR-51 — Help centre & articles. A user-facing help centre (accessible from every page) with instant client-side search over title/summary/keywords/content and article cards; plus a Help Articles admin (Fleet Admin+) with a WYSIWYG editor (headings, lists, links, tables, image upload), summary, keywords, published/draft state, ordering, and a “Visible to carriers” toggle (internal vs. owner-operator articles). Seeded starter guide content.
4.21 Partner API & Documentation
FR-52 — Partner API. A bearer-token REST API (tokens held in encrypted credentials; constant-time comparison) providing: a vehicle-telematics upsert endpoint (match by VIN, else unit number; single or batch; partial-success status) and a hours-of-service-ledger endpoint (three payload shapes: batch of duty-status changes / single change / upsert-and-replace; auto-create missing driver records tagged import_pending; idempotent per entry UUID; ruleset defaults from the driver profile). An in-app API documentation page (Platform Admin).
4.22 Navigation Configuration
FR-53 — Per-role navigation builder. A per-role sidebar builder (Platform Admin): a code registry of sections/items × role eligibility, a per-role layout store, and a resolver that reconciles them — configuration may reorder/rename/hide/move items but must never widen access; newly eligible items auto-appear. Drag-and-drop editor with reset-to-defaults per role; dynamic blocks (Dashboards, Reports, Load statuses) auto-generated and repositionable only.
4.23 Notification Templates
FR-54 — Notification templates. An admin-editable driver-assignment notification template (subject, title, intro, closing, signature) with merge fields (driver name, route ref, dispatch time, vehicle unit number, stop count) and a preview. The compliance-export summary is fixed/non-configurable.
4.24 Settings
FR-55 — Settings. A key-value settings store (Platform Admin), including at minimum a configurable hours-of-service reset threshold (default per applicable federal rule) used in eligibility routing; the schema/UI must accommodate additional keys.
4.25 Fuel Analytics (Optional / Future)
FR-56 — Fuel analytics helper (Optional). A standalone fuel-efficiency model estimating expected consumption per route, deviation flags, and a recommendation from a manufacturer efficiency curve. Not required to be wired into any screen in core scope; may be proposed as a follow-on item.
4.26 Reset / Maintenance Tooling (Temporary)
FR-57 — Maintenance tooling (Temporary). Development/staging maintenance utilities (e.g. bulk-clear of loads/routes/uploads with typed confirmation; seed/test-data tasks). Any such “Reset” screen is explicitly temporary and must be removable before go-live; it must not be exposed in production. Bidders should treat this as low-effort tooling, not a user feature.

A native or hybrid mobile app for drivers is mandatory; a browser-only fallback for driver workflows is not acceptable given field connectivity constraints.

Offline-capable mobile driver app for DVIR and hours-of-service entry in low-connectivity areas, with conflict-safe sync on reconnect.

Appendix A — Domain Model / Data Dictionary (summary)
The Platform comprises approximately 51 primary database tables (plus framework tables for background jobs, cache, and object storage). Bidders should size their proposal to this scale. The key entities, grouped by domain, are summarised below; the full field-level detail of the reference implementation is available in the source scope document on request.
A.1 Loads & workflow — loads (the central entity; FKs to vehicle, driver, carrier company, route, dispatch status, defect categories; captured data, eligibility snapshots, references, disposition fields; attached documents; reference VFOxxxxxxx). — load_status_logs (immutable audit trail; one row per transition; captured test data, batch/reverted flags). — dispatch_statuses (configurable states: name, colours, position, and text-array field/role/column configuration). — dispatch_status_transitions (allowed edges: from/to, outcome trigger, default target). — fault_codes; defect_categories; and exclusion join tables linking each lookup to vehicle types.
A.2 Catalogue — vehicle_types (class, default maintenance-interval template, source); carrier_aliases; legacy_vehicle_type_mappings; legacy_fault_mappings.
A.3 Telematics / ingestion — telematics_events (vehicle, timestamp, mileage, engine hours, location); duty_status_changes (driver, timestamp, duty status, source — source of truth for hours-of-service determination).
A.4 Compliance / dispatch — routes; load_routes (join); compliance_records (counts, cumulative hours, review lifecycle); carrier_companies (default thresholds); driver_hos_rulesets; legacy_mappings; vehicles.
A.5 Config / content / admin — users; settings; notification_templates; nav_role_layouts (jsonb); bulk_uploads (stateful import records with jsonb mapping/validation); dashboards → dashboard_panels → dashboard_widgets; help_articles.
A.6 Framework tables — Object storage (3 tables); background job queue (~9 tables); cache store.
