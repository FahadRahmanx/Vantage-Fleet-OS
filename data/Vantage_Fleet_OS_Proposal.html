1.Executive summary

We propose to design, build, test and deploy the Vantage Fleet OS platform in full, covering all fifty-seven functional requirements, both client applications, the Partner API and the data importers, across thirty-four weeks in seven accepted phases.

Vantage requires a single system to carry a load from intake through assignment, pre-trip inspection, dispatch, post-trip reconciliation, maintenance triage and compliance review, with the workflow itself held as configuration rather than compiled into the application. The requirement set is large but, with three exceptions, conventional. Those three exceptions carry nearly all of the technical risk in the engagement, and the RFP identifies them plainly in clause 5.2: the data-driven workflow engine, the hours-of-service reconciliation ledger, and the eligibility rules that must return identical answers on the server and inside the driver's mobile application.

Our delivery plan is organised around retiring those three risks in the first half of the schedule rather than distributing them across it. The workflow engine and audit trail are complete and accepted by week ten. Eligibility, outcome routing and the mobile foundation follow by week seventeen. The hours-of-service ledger, which is the requirement with the strongest correctness obligation, is built against a frozen configuration schema rather than a moving one.

Prototype evidence

We have built a working prototype of the three high-risk mechanics directly against this specification. It implements the configurable status and transition engine with flag-based column resolution, the four-state eligibility determination, a re-derived hours-of-service ledger, inspection outcome routing with override capture, and the immutable audit trail carrying eligibility snapshots. It is covered by thirty-three service-level tests and a transport-level suite that includes cross-company isolation checks. The estimates, sequencing and risk positions in this proposal are drawn from that build rather than from analogy, and the prototype is available for demonstration during evaluation.

Two findings from that work shape the proposal. First, resolving workbench columns by status flag rather than by status name removes risk R-3 by construction instead of by documentation, and costs nothing when done from the outset. Second, the reliable answer to risk R-2, drift between the mobile and server eligibility implementations, is not shared test fixtures but a single compiled rules package that both runtimes import. That is only achievable if the server and the mobile application share a language, which is the principal reason for the stack we propose in section 4.

2.Understanding of requirements

The platform is a company-scoped multi-tenant application with six roles and a platform-administrator flag layered above them. Owner-operator partners must see only their own loads, vehicles and documents, and that restriction has to hold at the data access layer rather than in the interface, across dashboards, navigation counts and help visibility alike. We read clause 4.1 as requiring capability rules derived from role rather than a fixed permission list per screen, and we have designed accordingly: authorisation is expressed as named capabilities evaluated server-side, so a rule such as dispatch-write can be granted to two roles and a super-user flag without being restated in every route.

The workflow engine is the structural centre of the system. Statuses carry position, behavioural flags, role-visibility arrays and field sets as data, and transitions carry an optional outcome trigger and a single default target. Every board, list column, permission to advance and audit entry derives from those two tables. The consequence, which we treat as a design obligation rather than a side effect, is that no screen may depend on a status name or code. The RFP notes under clause 4.11 that the reference implementation violates this in the workbenches; our implementation does not.

The hours-of-service ledger is the requirement with the least tolerance for error. Clause 4.14 states the invariant precisely: one reconciled ledger per driver per cycle, accumulated across all loads within a route, cleared at each qualifying reset, and attributed against the applicable ruleset resolved in priority order. We treat availability as a derived quantity that is recomputed on every read and never cached, and we test the invariant with generated duty sequences rather than fixed examples.

4.2Justification for departure from the reference stack

The reference implementation is Django, and we do not claim the functional set is easier to build in Node. The RFP is correct that the workflow engine, the ledger and the dual eligibility rules carry substantial effort regardless of stack. Our justification rests on one specific point rather than on general preference.

FR-27 requires the eligibility logic to operate consistently on the server and in the mobile application, and risk R-2 records drift between those implementations as medium-likelihood and high-impact, with a single source of truth stated as the preferred mitigation. With a Python server and a JavaScript mobile application, a single source of truth is not attainable; the mitigation necessarily degrades to shared fixtures testing two independent implementations, which detects drift after it occurs rather than preventing it. With one language across both runtimes, the eligibility and hours-of-service rules compile to a single package that the server imports directly and the mobile application bundles. There is then no second implementation that can drift, and the highest-impact risk in the register is closed by construction rather than monitored.

We note the trade-off honestly. If Vantage holds or intends to recruit Python engineering capability for long-term ownership, that is a legitimate reason to prefer the reference stack, and we are equally able to deliver on Django. In that case R-2 reverts to a monitored risk mitigated by shared fixtures, and we would propose a contract-test suite executed against both implementations on every build.

5.System architecture

The architecture separates a thin transport and authorisation layer from a services layer that holds the domain logic, with the workflow engine driven entirely by configuration rows. The shaded band in Figure 1 is the shared rules package described in section 4.2.

5.1Data model

Approximately fifty-one primary tables across six domains, consistent with Appendix A of the RFP: loads and workflow, comprising loads, status logs, dispatch statuses, transitions and the defect and fault catalogues; the reference catalogue and legacy mappings; telematics events and duty-status changes; compliance records, routes and carrier companies; configuration and content; and framework tables for storage, jobs and cache. Two rules hold throughout the model. Derived values are never stored, so route stage, driver eligibility and hours availability are computed on read and cannot go stale. Captured audit data is held as a single versioned JSON column on the status log rather than as a set of nullable snapshot foreign keys, which keeps each audit row immutable and self-contained.

5.2Dispatch workflow and outcome routing

Figure 2 shows the default configured workflow. Every box is a row in the status table and every arrow a row in the transition table, so the shape shown is configuration rather than code and an administrator can alter it without a release.

FR-28 specifies the outcome priority exactly, and we implement it as a pure function so that it is testable without a database: any out-of-service defect makes the overall outcome out-of-service; failing that, any minor defect makes it a minor defect; otherwise the inspection passes. The computed outcome selects the transition whose trigger matches it. A manual override bypasses that selection and requires a reason, which is validated before any write occurs, so an override without a reason cannot leave a partial record behind. Submitting an inspection and advancing the load occur within one database transaction, leaving no window in which an inspection exists without the status change it caused, or the reverse.

Workbench columns resolve by status flag only. Renaming a status in the workflow configuration screen therefore cannot break the Dispatch or Maintenance board, and we include that rename as an automated regression test rather than as a documented caveat, which is the improvement invited by the note under clause 4.11.

6.Delivery approach

6.1Method and cadence

Each phase concludes with a deployed increment on an agreed environment, a passing continuous integration run, and a demonstration against the specific requirements that phase claims, which is the acceptance definition given in clause 6.3. Within a phase we work in one-week iterations with a mid-phase review, so that a misread requirement surfaces within days rather than at the handover checkpoint. Requirements are tracked by FR number from proposal through to acceptance, so that at any point in delivery the status of each of the fifty-seven items is visible to both parties.

Scope control carries more weight here than on a typical engagement because clause 11.3 records creep on the configurable engine as the only risk rated high for both likelihood and impact. Our control is a configuration schema freeze at the end of phase two: after that checkpoint, additions to the status, transition or field-set schema are handled as change control rather than as refinement. A configurable system invites indefinite configurability, and this freeze is what prevents phase two from consuming phase four.

6.2Treatment of the three high-risk mechanics

  • Workflow engine. Statuses carry an explicit position, and direction is enforced by rank rather than by which edges happen to be configured: advance may move only to an equal or later position, revert only to an earlier one. This makes the backward-only rule of FR-31 structural. Two partial unique indexes make ambiguous auto-routing impossible at the database level, permitting one default target per source status and one transition per outcome per source status.
  • Hours-of-service ledger. Availability is re-derived from duty-status entries on every read and never cached, as risk R-6 requires. The single-reconciled-ledger invariant is expressed as a property test over generated duty sequences, including reset boundaries and overlapping assignments, rather than as example-based cases alone.
  • Dual eligibility. One compiled rules package imported by both runtimes, as set out in section 4.2. The mobile application calls the same function the server calls; the server remains authoritative and revalidates on submission.

6.4Testing and continuous integration

Continuous integration runs on every push and pull request and gates merge. Unit tests cover the eligibility rules, hours allocation, outcome routing and validation logic. Controller tests cover actions, authorisation gates and company scoping, and include a cross-company isolation case for every domain entity rather than for loads alone. End-to-end tests cover login, the full dispatch lifecycle, the advance modal across both the server and mobile eligibility paths, bulk upload, triage and compliance review. Mobile tests cover offline capture, synchronisation conflict resolution and device-loss handling. Dependency and code scanning are gated at zero high or critical findings, and the linter is gated at zero offences. As clause 5.6 anticipates, the duplicated client and server eligibility logic and the configuration-driven workflow receive disproportionate system-test coverage; in our case the shared rules package reduces the surface that must be tested twice to the call sites rather than the logic.

9.Security

Authorisation is enforced in the services and query layer, never in the interface alone, and company scoping is applied as a query predicate so that a missing filter fails closed. Passwords are hashed with Argon2id at a tuned work factor, and reset tokens expire within the six-hour window suggested in clause 4.2. Session cookies are HttpOnly, Secure and SameSite, cross-site request forgery protection is enabled everywhere except the Partner API namespace, and TLS is forced in production. Partner API tokens are held per partner in encrypted configuration and compared in constant time. Secrets live in encrypted configuration and appear in neither source nor logs. All input is validated server-side, queries are parameterised through the ORM, spreadsheet parsing runs with macro execution disabled and upload types are validated on content rather than extension. On mobile, offline data is held in encrypted local storage behind device-bound tokens with remote wipe available for lost devices. Dependency and static code scanning run in the pipeline and gate merge.
