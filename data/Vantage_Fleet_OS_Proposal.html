1.Executive summary

We propose to design, build, test and deploy the Vantage Fleet OS platform in full: all fifty-seven functional requirements, both client applications, the Partner API and the data importers, across thirty-four weeks in seven accepted phases.

Vantage requires one system to carry a load from intake through assignment, pre-trip inspection, dispatch, post-trip reconciliation, maintenance triage and compliance review, with the workflow held as configuration rather than compiled into the application. The requirement set is large but, with three exceptions, conventional. Those exceptions carry nearly all of the technical risk, and the RFP identifies them plainly in clause 5.2: the data-driven workflow engine, the hours-of-service reconciliation ledger, and the eligibility rules that must return identical answers on the server and inside the driver's mobile application.

Our plan retires those three risks in the first half of the schedule rather than spreading them across it. The workflow engine and audit trail are accepted by week ten; eligibility, outcome routing and the mobile foundation by week seventeen. The hours-of-service ledger, the requirement with the strongest correctness obligation, is then built against a frozen configuration schema rather than a moving one.

Prototype evidence

We have built a working prototype of the three high-risk mechanics against this specification: the configurable status and transition engine with flag-based column resolution, four-state eligibility determination, a re-derived hours-of-service ledger, inspection outcome routing with override capture, and the immutable audit trail carrying eligibility snapshots. It carries thirty-three service-level tests and a transport-level suite including cross-company isolation checks. The estimates and risk positions below are drawn from that build rather than from analogy, and it is available for demonstration during evaluation.

Two findings from that work shape this proposal. Resolving workbench columns by status flag rather than by name removes risk R-3 by construction instead of by documentation, and costs nothing when done from the outset. And the reliable answer to risk R-2, drift between the mobile and server eligibility implementations, is not shared test fixtures but a single compiled rules package both runtimes import, which is achievable only if server and mobile share a language. That is the principal reason for the stack proposed in section 3.

3.1Justification for departing from the reference stack

We do not claim the functional set is easier in Node; the RFP is correct that the engine, the ledger and the dual eligibility rules carry effort regardless of stack. The justification rests on one point. FR-27 requires eligibility logic to behave identically server-side and in the mobile app, and R-2 rates drift between those implementations medium-likelihood and high-impact with a single source of truth as the preferred mitigation. With a Python server and a JavaScript mobile app that is unattainable, and the mitigation degrades to fixtures that detect drift after it occurs. With one language, the rules compile to a single package the server imports and the mobile app bundles, so no second implementation exists to drift. If Vantage intends to hold Python capability for long-term ownership, that is a legitimate reason to prefer the reference stack and we are equally able to deliver on Django; R-2 then reverts to a monitored risk with contract tests executed against both implementations.

4.System architecture

A thin transport and authorisation layer sits above a services layer holding the domain logic, with the workflow engine driven entirely by configuration rows. The shaded band in Figure 1 is the shared rules package described above.

The data model comprises approximately fifty-one primary tables across six domains, consistent with Appendix A: loads and workflow; the reference catalogue and legacy mappings; telematics events and duty-status changes; compliance records, routes and carrier companies; configuration and content; and framework tables. Two rules hold throughout. Derived values are never stored, so route stage, eligibility and hours availability are computed on read and cannot go stale. Captured audit data is held as one versioned JSON column on the status log rather than a set of nullable snapshot keys, keeping each audit row immutable and self-contained.

4.1Dispatch workflow and outcome routing

Figure 2 shows the default configured workflow. Every box is a row in the status table and every arrow a row in the transition table, so the shape shown is configuration rather than code and an administrator can alter it without a release.

FR-28 specifies the outcome priority exactly and we implement it as a pure function, testable without a database: any out-of-service defect makes the outcome out-of-service; failing that, any minor defect makes it a minor defect; otherwise the inspection passes. The computed outcome selects the transition whose trigger matches. A manual override bypasses that selection and requires a reason, validated before any write, so an override without a reason cannot leave a partial record. Submitting an inspection and advancing the load occur in one transaction, leaving no window in which an inspection exists without the status change it caused. Workbench columns resolve by status flag only, so renaming a status cannot break the Dispatch or Maintenance board; that rename is an automated regression test rather than a documented caveat, which is the improvement invited by the note under clause 4.11.

5.Approach

Each phase concludes with a deployed increment on an agreed environment, a passing integration run, and a demonstration against the requirements that phase claims, which is the acceptance definition at clause 6.3. Within a phase we work in one-week iterations with a mid-phase review, so a misread requirement surfaces in days rather than at the handover checkpoint. Requirements are tracked by FR number from proposal to acceptance, so the status of each of the fifty-seven items is visible to both parties throughout.

Scope control carries more weight here than usual because clause 11.3 rates creep on the configurable engine high for both likelihood and impact. Our control is a configuration schema freeze at the end of phase two, after which additions to the status, transition or field-set schema are change control rather than refinement. A configurable system invites indefinite configurability, and this freeze is what stops phase two consuming phase four.

5.1The three high-risk mechanics

  • Workflow engine. Statuses carry an explicit position and direction is enforced by rank rather than by which edges happen to exist: advance may move only to an equal or later position, revert only to an earlier one, making the backward-only rule of FR-31 structural. Two partial unique indexes make ambiguous auto-routing impossible at the database level, permitting one default target per source status and one transition per outcome per source status.
  • Hours-of-service ledger. Availability is re-derived from duty-status entries on every read and never cached, as R-6 requires. The single-reconciled-ledger invariant is a property test over generated duty sequences covering reset boundaries and overlapping assignments, not example cases alone.
  • Dual eligibility. One compiled rules package imported by both runtimes. The mobile application calls the same function the server calls; the server remains authoritative and revalidates on submission.

Non-functional requirements. Board and list queries run against covering indexes with eager loading so no page issues per-row queries, and the NFR-1 budgets are asserted in the pipeline against a seeded dataset so a regression fails the build. Stateless workers behind a load balancer with sessions in Redis meet NFR-2, load tested at eighty internal and two hundred and fifty mobile sessions in phase seven. Rolling zero-downtime deployments and daily backups with a rehearsed restore meet NFR-3. The browser matrix of NFR-4 is covered in the end-to-end suite. WCAG 2.1 AA contrast, keyboard-navigable primary flows and labelled controls are audited automatically and by manual traversal of the dispatch and inspection paths for NFR-5. Offline capture writes to a local append-only queue with client-generated identifiers, so replay on reconnection is idempotent and lossless for NFR-6. Every status change writes one immutable log row carrying actor, timestamps, statuses, captured inspection data, eligibility snapshot, stop count and flags, never updated or deleted by application code, for NFR-7.

Security. Authorisation is enforced in the services and query layer rather than the interface, with company scoping applied as a query predicate so a missing filter fails closed. Passwords use Argon2id at a tuned work factor with a six-hour reset window; session cookies are HttpOnly, Secure and SameSite; cross-site request forgery protection is enabled everywhere except the Partner API namespace; TLS is forced in production. Partner tokens are held per partner in encrypted configuration and compared in constant time. Secrets appear in neither source nor logs. Input is validated server-side, queries are parameterised, spreadsheets parse with macros disabled, and uploads are validated on content rather than extension. Mobile offline data sits in encrypted local storage behind device-bound tokens with remote wipe.

8.Commercial terms and assumptions

We offer a defect-fix warranty of sixty days from production go-live, exceeding the thirty-day minimum at clause 10.1. Ongoing support is offered against four severity levels, from one-hour response and same-day resolution for a production outage through to next-release handling of cosmetic defects, and we will align hours and targets with the values Vantage completes at clause 10.2. All source, deliverables, documentation and associated intellectual property are owned by Vantage and developed in a Vantage-controlled repository from the first commit rather than transferred at completion; every third-party component is disclosed with its licence, and we incorporate no pre-existing vendor intellectual property that is not licensed to Vantage on a perpetual, royalty-free basis. Handover delivers architecture and data-model documentation, deployment and operational runbooks, Partner API documentation and an administrator configuration guide covering the workflow engine, the ledger and the settings store, followed by knowledge-transfer sessions run against the live system.

Consistent with clause 11.1 we assume Vantage provides telematics sandbox access, the SMS gateway and object storage account, reference and seed data, and a production hosting environment unless we are separately engaged for managed hosting; that a purchased administration theme is acceptable and bespoke visual design is a follow-on item; that rulesets are expressed per applicable federal exemption category; and that staff are available for phase reviews and acceptance testing within one week of each handover, failing which the affected phase boundary moves rather than the following phase compressing. The functional requirements in the RFP are treated as authoritative where they conflict with the reference implementation.
